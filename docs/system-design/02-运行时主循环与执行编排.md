# 运行时主循环与执行编排

这篇文档讲一条用户消息进入 runtime 后，怎么被推进成一次完整 run。

## 这层解决什么问题

用户只发一句话，但系统要做很多事：

- 找到 session。
- 建立 run 状态。
- 调插件。
- 路由到 bot 或 coding。
- 构建上下文。
- 调模型。
- 执行工具。
- 写 trace 和报告。
- 更新记忆。
- 发出回复。

这些动作的编排中心是 `runtime/agent_loop.py`。

更底层的模型-工具循环在 `runtime/reasoning_loop.py`。

## AgentLoop.run_once()

`AgentLoop.run_once()` 是一轮 inbound 的主入口。

它按顺序做这些事：

1. 从 `MessageBus` 取出 inbound。
2. 根据 `inbound.session_key` 获取或创建 session。
3. 应用 inbound 身份。
4. 创建 `RunState` 并写入 trace。
5. 执行 `plugin_manager.before_turn()`。
6. 用 `ModeRouter` 选择 route。
7. 把用户消息写入 session。
8. 根据 route 决定走 coding task session 还是普通 pipeline。
9. 执行 `plugin_manager.after_turn()`。
10. 完成 run，写 run state/report/trace。
11. 保存 session。
12. 发布 outbound 回复。

如果中间抛异常，会走 `_fail_run()`，把 run 标记为 failed 并写错误。

## RunState 的作用

`RunState` 是一次执行的状态对象。

创建时会记录：

- `run_id`
- `session_id`
- `channel`
- `chat_id`
- `user_id`
- `user_role`
- 当前 mode
- execution path
- started time
- metadata

运行中会更新：

- route 结果
- reasoning steps
- tool calls
- last tool
- stop reason
- final answer
- error
- finished time

`AgentLoop._start_run()` 会把 `active_run_id` 和 `last_run_id` 写到 session metadata。这让 session 能知道当前正在跑哪个 run。

## 路由之后的两条路径

路由结果由 `ModeRouter.route()` 给出，里面包含：

- intent
- execution
- profile
- tool_mode
- confidence
- reason
- switched

如果 `route.switched` 为 true，说明这轮只是切换模式。系统会直接回复切换消息，不进入模型推理。

如果 profile 的 `tool_mode == "coding"`，进入：

```python
self.task_session_runner.run_coding_task(...)
```

否则进入：

```python
self.pipeline.run(...)
```

## Pipeline 的职责

`Pipeline` 当前主要负责 turn 级编排：

- turn 前 reset 工具状态。
- 对 session messages 做 `micro_compact`。
- 超过阈值时执行 `auto_compact`。
- 在每个 reasoning step 前构建 context。
- 决定模型 purpose：coding profile 用 `coding`，否则用 `chat`。
- reasoning loop 结束后触发 memory lifecycle。

`Pipeline` 不直接执行模型工具循环。它把这部分交给 `AgentRunner` 和 `ReasoningLoop`。

## ReasoningLoop 的职责

`ReasoningLoop.run()` 是模型-工具循环。

每一轮 reasoning step 会做：

1. 检查是否超过 `max_reasoning_steps`。
2. 记录 reasoning step 到 run state。
3. trace `reasoning.step.started`。
4. 调 `build_context(session, profile)` 构建模型 messages。
5. trace context build start/completed。
6. 调 provider 的 `chat` 或 `stream_chat`。
7. 把模型返回的 assistant message 写回 session。
8. 如果没有 tool calls，本轮结束。
9. 如果有 tool calls，逐个执行工具。
10. 把 tool result 写回 session。
11. 根据 loop guard、不可用工具、reflection 决定继续或停止。

这是一条标准的：

```text
context -> model -> assistant/tool_calls -> tool results -> context -> model
```

闭环。

## 停止条件

当前主要停止条件有：

- 模型返回无 tool call 的 assistant final message。
- reasoning steps 超过上限。
- 工具循环保护触发。
- 模型重复请求当前不可用工具。
- reflection agent 要求 stop。
- provider 或工具执行异常导致 run failed。

停止时如果是正常 final，会调用 `after_turn(session)`；如果是保护性停止，会写一条 assistant guard message。

## Trace 如何嵌入主循环

主循环不是跑完才补 trace。关键节点会立即写事件：

- `run.started`
- `inbound_received`
- `route_selected`
- `reasoning.step.started`
- `context.build.started`
- `context.build.completed`
- `model.call.started`
- `model.call.completed`
- `model.call.failed`
- `tool.call.started`
- `tool.call.completed`
- `tool.call.failed`
- `run_finished`
- `run.failed`

这些事件会进入 `.runs/<run_id>/trace.jsonl`。

## 当前边界

运行时主循环已经有清晰 run 边界和 trace，但还没有这些能力：

- run 中断后从某个 step 恢复。
- 持久化工作队列。
- 多 worker 并发调度。
- 人类审批后继续执行。

当前系统更准确的定位是：单进程、多入口、有状态、可追踪的 agent runtime。

## 总结

`AgentLoop` 决定一条 inbound 怎么变成一次 run。`Pipeline` 决定一个 turn 怎么准备上下文、压缩历史和更新记忆。`ReasoningLoop` 决定模型和工具如何循环。

三者分工合起来，构成了当前项目的主执行链。
