# 上下文构建、压缩与记忆生命周期

这篇文档讲当前项目如何把 session、memory、inbox 和后台结果组合成模型上下文，以及一轮结束后如何更新记忆。

## 这层解决什么问题

模型每轮看到的不是完整数据库，也不是随便拼接的字符串。

当前上下文构建由 `runtime/context.py` 的 `ContextBuilder` 负责，turn 前压缩由 `runtime/pipeline.py` 负责，派生记忆更新由 `memory/lifecycle.py` 负责。

这层要解决的问题是：

- system prompt 从哪里来。
- 不同 agent 模式的长期 instructions 从哪里来。
- session messages 怎么进入模型。
- memory 怎么作为上下文附加。
- background task 和 teammate inbox 怎么进入 task session。
- 历史过长时怎么压缩。
- 一轮结束后怎么留下可复用记忆。

## ContextBuilder 的输出

`ContextBuilder.build()` 返回：

```python
@dataclass
class ContextBundle:
    messages: list[dict]
    report: ContextBuildReport | None = None
```

它不是返回一个大 prompt 字符串，而是返回 chat messages，并附带一份 context build report。

实际发送给模型的 messages 仍然保持很少的形态：

```text
system message
session history messages
optional context frame user message
```

也就是说，逻辑 section 和 chat message 不是一一对应关系。section 是 runtime 用来统计、预算、裁剪和 trace 的内部结构；chat message 是 provider 最终看到的传输结构。

构建顺序是：

1. 构建 system prompt。
2. 按 profile 加载 `.agent/` 和项目 instruction 文件。
3. 从 memory store 构建 `<memory>` block。
4. 构建 context frame。
5. 返回 `[system, *session.messages, context_frame]`。

`ContextBuildReport` 会记录本轮上下文的逻辑 section 统计，例如：

- `system_profile`
- `mode_instructions`
- `project_instructions`
- `runtime_guidance`
- `system_prompt`
- `conversation_history`
- `current_request`
- `memory`
- `task_runtime_events`
- `inbox`
- `background_results`
- `context_frame`

每个 section 会记录：

- raw chars
- rendered chars
- budget chars
- truncated
- metadata

当前实现已经支持第一版 section budget。默认关闭；开启后会先裁剪低风险、可再生的 section，并把裁剪原因写入 `ContextBuildReport.reductions`。

## logical sections vs messages

当前系统采用“逻辑层细，传输层简”的设计。

逻辑层：

```text
system_profile
mode_instructions
project_instructions
runtime_guidance
conversation_history
current_request
memory
task_runtime_events
```

传输层：

```python
messages = [
    {"role": "system", "content": system_prompt},
    *session.messages,
    {"role": "user", "content": context_frame},  # optional
]
```

其中：

- `system_profile`、`mode_instructions`、`project_instructions`、`runtime_guidance` 会合并成一条 system message。
- `conversation_history` 对应 session messages 中除最新用户请求外的历史消息。
- `current_request` 是 session messages 中最新的 user message，只在 report 中单独标记，不重复注入。
- `memory` 和 `task_runtime_events` 当前会合并进可选的 context frame user message。

这样做的好处是：runtime 内部可以精细统计和预算，但不会把 provider 侧 message 结构搞得很碎。

## section budget V1

section budget 由 `runtime/context_budget.py` 的 `ContextBudgeter` 负责，`ContextBuilder` 在逻辑 section 构建完成后、实际 messages 装配前调用它。

默认配置在 `.env.example` 中：

```text
CONTEXT_ENABLE_SECTION_BUDGET=0
CONTEXT_BUDGET_CHARS=24000
CONTEXT_MODE_INSTRUCTIONS_BUDGET=3000
CONTEXT_PROJECT_INSTRUCTIONS_BUDGET=3000
CONTEXT_MEMORY_BUDGET=2500
CONTEXT_TASK_RUNTIME_EVENTS_BUDGET=2000
CONTEXT_MODE_INSTRUCTIONS_FLOOR=1000
CONTEXT_PROJECT_INSTRUCTIONS_FLOOR=1000
CONTEXT_MEMORY_FLOOR=500
CONTEXT_TASK_RUNTIME_EVENTS_FLOOR=300
```

V1 只裁剪这些 section：

- `mode_instructions`
- `project_instructions`
- `memory`
- `task_runtime_events`

V1 不裁剪：

- `session.messages`
- `conversation_history`
- `current_request`

这意味着最新用户请求永远不会被这层预算逻辑截断。历史消息如果过长，仍然交给 turn 前压缩流程处理。

各 section 的默认裁剪策略：

- `mode_instructions`：保留头部。通常规则文件越靠前越基础。
- `project_instructions`：保留头部。项目约定优先保留开头的总则和命令。
- `memory`：保留头尾。头部可能是稳定偏好，尾部可能是最近沉淀。
- `task_runtime_events`：保留尾部。后台任务和 teammate 事件更看重新近结果。

如果触发裁剪，report 中会记录：

```json
{
  "section": "memory",
  "reason": "section_budget",
  "before_chars": 4200,
  "after_chars": 2500,
  "budget_chars": 2500,
  "floor_chars": 500,
  "effective_budget_chars": 2500,
  "strategy": "head_tail"
}
```

同时，对应 section 的 `truncated` 会变成 `true`，`budget_chars` 会写入该 section 的预算值。

## system prompt

system prompt 由 profile 提供：

```python
profile.system_prompt
```

然后追加几条 runtime 级规则：

- 用户问过去偏好或项目约定时使用 `recall_memory`。
- 用户表达持久偏好或重要事实时使用 `memorize`。
- 有些工具是 deferred，需要用 `tool_search` 查找或解锁。

这说明工具发现和记忆使用不是只靠业务 profile，而是 runtime 会统一注入基础规则。

## instruction files

`ContextBuilder` 现在会按 `profile.tool_mode` 读取不同 instruction 文件。

聊天 / bot 模式读取：

```text
.agent/assistant.md
```

coding 模式读取：

```text
.agent/coding.md
AGENTS.md
```

`.agent/assistant.md` 用于主线聊天助手，主要放：

- 助手角色和语气。
- 用户协作偏好。
- memory 使用边界。
- 普通工具使用原则。
- 不暴露敏感信息、不编造项目状态等基础约束。

`.agent/coding.md` 用于 coding agent，主要放：

- 代码修改工作流。
- workspace 安全边界。
- 大文件读取策略。
- git 和 shell 工具使用约束。
- 完成后的验证和报告要求。

`AGENTS.md` 是 workspace / 项目级规则。它只在 coding 模式下注入，用来承载当前项目的构建命令、测试方式、代码风格和项目约定。

instruction 文件会包在 system prompt 中：

```text
<instructions source=".agent/coding.md">
...
</instructions>
```

每个 instruction 文件有长度上限，超出后会被截断，避免一份规则文件直接吃满上下文。

在 context report 中，这些文件不会直接作为顶层逻辑 section 展开，而是聚合到：

- `mode_instructions`
- `project_instructions`

具体文件来源记录在 section metadata 的 `sources` 和 `files` 中。

## memory block

如果配置了 memory store，`ContextBuilder` 会读取：

```python
store.read_all()
```

如果 store 支持 `for_session`，会先根据 session 取作用域内 memory：

```python
if hasattr(store, "for_session"):
    store = store.for_session(session)
```

最终格式是：

```text
<memory>
...
</memory>
```

这个 memory block 会作为一个额外 user message 附在当前上下文末尾。

## context frame

context frame 目前包含三类内容：

- memory block
- teammate inbox
- background results

inbox 会被 JSON 格式化后放入：

```text
<inbox>
...
</inbox>
```

background results 会放入：

```text
<background-results>
[bg:<task_id>] <status>: <result>
</background-results>
```

`Pipeline._should_include_task_runtime_events()` 会限制这些内容只在 task session + coding profile 下进入上下文。

## 压缩策略

当前压缩发生在 `Pipeline`：

```python
micro_compact(session.messages)
if estimate_tokens(session.messages) > THRESHOLD:
    session.messages[:] = auto_compact(session.messages)
    session.mark_compacted()
```

它会在两个位置执行：

- turn 开始前。
- 每个 reasoning step 构建上下文前。

这说明当前压缩粒度是 session messages，不是 Pico 那种按 prefix/memory/history/relevant memory 分段预算治理。

## context sanitize

`ReasoningLoop._reasoning_step()` 在发给 provider 前会执行：

```python
context_messages, dropped_messages = _sanitize_context_messages(context.messages)
```

如果有非法或空消息被丢弃，会写 trace：

```text
context.sanitized
```

这个机制主要用于 provider 兼容和请求安全，避免把不合规 chat message 发给模型。

## context report trace

`ReasoningLoop` 在 `context.build.completed` 事件中会写入：

```json
{
  "context_summary": {
    "message_count": 3,
    "estimated_tokens": 1234
  },
  "context_report": {
    "total_chars": 4567,
    "sections": {
      "conversation_history": {
        "raw_chars": 1000,
        "rendered_chars": 1000,
        "truncated": false
      }
    }
  }
}
```

这让 trace viewer 可以解释：本轮模型到底看到了哪些上下文来源，以及每类上下文大概占了多少空间。

## MemoryLifecycle

普通 turn 结束后，`Pipeline._after_turn()` 会调用：

```python
self.memory_lifecycle.after_turn(session)
```

`MemoryLifecycle.after_turn()` 做这些事：

1. 找最近一条 user text 和 assistant text。
2. 如果用户显式说“记住”，直接写入 memory。
3. 如果文本像偏好或项目约定，写入 pending memory。
4. 用 summarizer 总结 assistant 回复。
5. 写入 history。
6. 更新 recent turns。
7. 超出 recent limit 的 turn 写入 archive store。

## 显式记忆和候选记忆

显式记忆通过 marker 检测，例如：

- `记住`
- `请记住`
- `帮我记住`
- `以后记得`
- `remember that`
- `please remember`

候选记忆通过关键词判断，例如：

- `我喜欢`
- `我的偏好`
- `这个项目`
- `代码风格`
- `用 pytest`
- `prefer`

候选会进入 pending，而不是直接变成长期 memory。

## 用户作用域

全局 memory store 在 `runtime/bootstrap.py` 中是：

```python
memory_store = ScopedMemoryStore(WORKDIR, legacy_store=MemoryStore())
```

`ScopedMemoryStore.for_session(session)` 会根据 user/session 解析 memory root。

这让不同用户的 memory 可以隔离。

## Coding task 的记忆不同

coding task session 使用 task-local memory：

```python
task_memory = MemoryStore(record.memory_root)
```

任务开始时会 seed：

- parent session id
- task request
- task-local memory 使用规则
- recent context

任务结束后会抽取 conclusions，再由 `TaskMemoryPromoter` 决定哪些候选可以进入 global pending memory。

所以 coding 中间过程不会直接污染全局长期记忆。

## 当前边界

当前上下文系统还没有：

- 分段 token budget。
- 语义检索式 relevant memory。
- 全仓代码索引。
- prompt cache key 管理。
- workspace summary 自动刷新进 prefix。
- 基于 section report 的自动裁剪。
- 独立的 `workspace_baseline` 和 `relevant_memory` section。

现在的机制更轻：system prompt + mode instructions + session messages + memory block + task runtime events + message compaction + provider sanitize。

## 总结

当前上下文构建的核心是保持简单和可控。

`ContextBuilder` 负责把 profile、mode instructions、session、memory 和 task runtime events 拼成 messages；`Pipeline` 负责压缩；`MemoryLifecycle` 负责 turn 后派生记忆。它还不是复杂 RAG，但已经有用户作用域、task-local memory、pending promotion 和按模式分离的 instruction 文件这些关键边界。
